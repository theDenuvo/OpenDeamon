## P0 — сломанное enforcement и зависший процесс

### 1. `quota-watch` не срабатывает: `matcher: "*"` — невалидный regex

**СТАТУС: ЗАКРЫТО (`d45891c`).** `matcher` заменён валидным regex по списку инструментов — это допустимый вариант из Фазы 1.1, а не удаление поля.


**Ошибка.** В `hermes-home/config.yaml:78` для quota-watch указан
`matcher: "*"`. Hermes компилирует matcher как regex
(`shell_hooks.py:110`); `"*"` не компилируется, срабатывает fallback
`treating as literal equality` (`shell_hooks.py:113`). Литeral `"*"` не
равен ни одному имени инструмента → хук зарегистрирован и не вызывается
никогда. Подтверждение в `hermes-home/logs/errors.log`:

```
2026-09-30 15:03:26,774 WARNING agent.shell_hooks: shell hook matcher '*'
is invalid (nothing to repeat at position 0) — treating as literal equality
```

**Предложение.** Убрать поле `matcher` у quota-watch: в `_TOOL_EVENTS`
matcher опционален, а отсутствие поля по коду (`shell_hooks.py:118`)
означает «срабатывать на все инструменты» — это и нужно. Если поле
требуется форматом, заменить на валидный regex, покрывающий весь
алфавит (например `terminal|write_file|patch|edit|code_execution|execute_code|delegate_task|web_search|...`),
и обязательно перепроверить логом, что WARNING исчез. Пункт 4 (парсер) —
независимый баг, его тоже надо закрыть, иначе фикс matcher ничего не
даст.

### 2. `quota-watch` парсит устаревшую схему `/credits` → все поля `null`

**СТАТУС: ЗАКРЫТО (`d45891c`).** Переход на `/api/v1/key`, 10 тестов зелёные.


**Ошибка.** `functions/quota-watch/quota_watch.py:100-114` ждёт от
`GET /api/v1/credits` вложенную структуру `data.usage.limit.daily_free_models`.
Живой ответ сейчас плоский:

```json
{"data":{"total_credits":10,"total_usage":0}}
```

Из него `usage = d.get("usage") or {}` → `{}`, поэтому `total_usage`,
`limit_usd`, `free_used`, `free_limit` все `None`. `verdict()`
(`quota_watch.py:140`) при `used is None` возвращает `allow`, то есть даже
после фикса matcher хук пропустит всё. Косвенное подтверждение:
`hermes-home/cache/quota-watch.json` содержит ровно `{"known": true,
"total_usage": null, ...}` — то есть схема не совпала при живом вызове.
Тесты этого не ловят: `test_quota_watch.py` мокает старую форму и зелёный.

Реальные лимиты лежат на другом эндпоинте (проверено живым вызовом):
`GET /api/v1/key` → `limit: 1`, `limit_reset: daily`,
`free_model_daily_requests: {used: 0, limit: 1000, remaining: 1000}`,
`usage_daily/weekly/monthly: 0`.

**Предложение.** Перевести `fetch_credits`/`measure` на `/api/v1/key`
(эндпоинт отдаёт и дневной бакет, и траты — оба порога нужны), удалить
ветку с `daily_free_models`. Тесты переписать на реальную форму ответа
(`/api/v1/key`), добавить кейс «плоская схема не должна молча давать
allow». Стоит зафиксировать в docstring, что оба эндпоинта наблюдались
живьём и схема меняется.

### 3. `comfy_gen.py` не забирает готовый результат: два бага, 15 минут впустую

**СТАТУС: ЗАКРЫТО.** Рабочая модель зафиксирована: Qwen-Image-2.1 (Uncensored) fp8 (`comfy_gen.py:13`).


**Ошибка.** Два независимых дефекта в `functions/imggen/comfy_gen.py`:

*a) Строка 193:* `q = f"/view?filename={images[0]}}&subfolder={'subfolder'}"`
— литерал `'subfolder'` вместо значения из ответа. Проверено живьём против
локального ComfyUI:

```
/view?filename=opendeamon_00001_.png&subfolder=           -> 200, 1 833 320 байт
/view?filename=opendeamon_00001_.png&subfolder=subfolder  -> 404
```

*b) Строка 178:* `hist = api(f"/history/{client_id}")` — ComfyUI ключирует
историю по `prompt_id`, а не по `client_id`. Клиент опрашивает
несуществующий ключ 900 секунд и падает с `TimeoutError`.

Симптом, наблюдаемый прямо сейчас: pid 25068 (`comfy_gen.py ... --size
1024x1024 --json`) висит с 18:02:51, CPU 0.5 с; очередь ComfyUI пуста

opendeamon_00001_.png` (1.8 МБ) **уже записана диском в 18:05:03** — то
есть генерация отработала успешно, а клиент её не увидел. Тот же
`TimeoutError: no image after 900s` уже зафиксирован в `_setup_tmp/qc.json`.

**Предложение.** Сохранять `prompt_id` из ответа `POST /prompt` (поле
`prompt_id` в JSON-ответе) и опрашивать `/history/{prompt_id}`. Для
`subfolder` брать `img.get("subfolder", "")` и `img.get("type", "output")`
из той же записи истории. После правки — прогнать на 1024×1024 и
убедиться, что клиент завершился за ~2 мин (131 с по логу ComfyUI) и
`qc.json` содержит `"ok": true`. Параллельно имеет смысл добавить в
`generate()` проверку: если очередь пуста, а deadline близко — вернуть
диагностику, а не молчаливый TimeoutError.

#### Р1. ✅ ЗАКРЫТО (`cb59567`) — проверка критерия потеряна не была

`mechanical.py:356` вызывает `run_clean(worktree)` **без аргумента
`spec`**. `_commands(spec, sandbox)` (строка 170) ждёт этот аргумент,

Воспроизведено: критерий «add складывает два числа», у него
проверка-скрипт, который **намеренно падает** на баге `add(2,3)!=5`, все

```
run exit=0  cmd=...python.exe test_alpha.py     <- запущен чужой тест
status_after: verified                          <- критерий не проверялся
```

**Почему это блокер.** `verified` сейчас означает «в дереве нашёлся

может объявить любые критерии и получить `verified`, если хоть один тест
проходит. Это ровно тот класс подмены, против которого построен проект.
Античит при этом исправен — он защищает тесты от изменения, но не
проверяет, что критерии чем-то подтверждены.

**Дополнительно:** строка 396 `status_after = "verified" if
unverifiable == 0` считается агрегатом по всему спеку, без привязки
«критерий → выполненная проверка». Поэтому даже после починки вызова
нужна таблица доказательств по каждому критерию, иначе `method: test`
с невыполненным `check` так же даст `verified`.

**ЗАПРОС:** починить вызов и добавить приёмочный тест

### Слой 3 — state machine воркера (код)

```
NOT_STARTED → RUNNING → COMPLETED
                       → FAILED_CLEAN   (упал до правок, откат не нужен)
                       → FAILED_DIRTY   (упал после правок)
FAILED_DIRTY → откат (КОД, не модель — /rollback это слотовая команда,
              не агентский тул)
   ├ успех  → BASELINE RESTORED → можно rework
   └ провал → RECOVERY_BLOCKED
```

`RECOVERY_BLOCKED` — **терминальный карантин**: никакого нового
worker run, никакого rework, никакого reuse этого worktree до явной
очистки человеком.

**Маркер карантина — на диске**, не в памяти: перезапуск процесса не
должен сделать загрязнённую среду снова пригодной. Четыре поля:
worktree identity, baseline/checkpoint identity, reason, timestamp.

Причины отката могут не сработать: файл вне worktree, файл занят
процессом, внешний артефакт, ресурс за пределами snapshot scope. Именно
поэтому карантин терминален — иначе защита становится бесконечным
источником грязных повторов.

### Слой 5 — рецензент (код)

0. **⚠️ ОБЯЗАТЕЛЬНО: `max_tokens` ≥ 700 и `response_format: json_object`.**
   `gpt-oss` — reasoning-модель и съедает бюджет токенов на размышление.
   Замерено на Groq: `max_tokens=10 → content=''`, `32 → content=''`,
   `64 → 'K'`, `200+ → нормальный текст`. **HTTP-код во всех случаях
   200** — сломанный вердикт неотличим от успешного по коду ответа.

   **Почему это ломает слой 5, а не тест:** при пустом `content` парсер
   получит `None`, и работа воркера будет отвергнута как «вердикта нет».
   Никакого сообщения об ошибке не возникнет — тихая поломка. Проверять
   не HTTP-код, а непустой `content` и валидный JSON.
   На вердикт уходит ~40-75 токенов reasoning до первого полезного
   токена. `temperature: 0` обязателен — вердикт должен быть
   воспроизводимым.

1. **Читает diff коммита, не живой workspace.** Это устраняет TOCTOU:
   рецензент анализирует ровно то состояние, которое прошло механику.
2. `WORKER_CLAIM` — в конце, с наименьшим доверием, изолирован.
   `DIFF`, `TEST_RESULTS`, `HASHES`, `CHANGED_FILES` собирает **код** из
   фактического состояния, не воркер. Иначе воркер формирует для
   ревьюера выгодную картину.
3. Capsule **~2000 токенов = target, не cap.** Замерено: типичная задача
   даёт ~2 600 токенов диффа, целый коммит из 7 файлов — 18 249. То
   есть отбор релевантных хунков обязателен, а таргет достижим.
4. **Не влезает → дробить по логическим группам изменений**, не
   расширять (у Groq потолок 8000 токенов/мин жёстко) и не резать
   механически по файлам (убивает связь `parser → AST → transform → test`).
5. Scheduler считает **`prompt + completion`**, не только input.
6. Порядок усечения: первым полный stdout, boilerplate, нерелевантные

7. Новые тесты рецензент классифицирует: `contract` / `supporting` /

   отличить не может — это вопрос намерения, а не структуры.
8. **NIM при переполнении отдаёт 503, а не 429.** Обрабатывать оба, иначе

### Слой 6 — независимость и вердикт (код)

```
FULL    = другой провайдер И другая модель
PARTIAL = другая модель, тот же провайдер
SEVERE  = тот же провайдер И та же модель
```

`SEVERE ⇒ task_status ≠ verified`, но **результат выдаётся** с пометкой
в первой строке вердикта. Блокировка превращала «проверенный результат
+ то же мнение» в «ничего» ровно тогда, когда провайдеры лежат.

Комбинация, которую надо вычислить: OpenRouter упал (ядро на NIM) и
Groq упал (ревьюер на NIM) ⇒ `Core = NIM` и `Reviewer = NIM` ⇒ `SEVERE`.
Система обязана это обнаружить, а не заявить независимость.

Типизация фейлов и что с ними:

| Тип | Действие |
|---|---|
| `SPEC_FAILURE` | rework спеки, не кода |
| `MECHANICAL_FAILURE` | rework кода, 1 цикл |
| `TEST_TAMPERING` | **эскалация, никогда rework** |
| `REVIEW_FAILURE` | rework кода, 1 цикл |
| `INFRA_FAILURE` | смена маршрута, **не** rework кода |
| `WORKER_CRASH` | откат к baseline, **не** повтор того же промта |

`TEST_TAMPERING` и `WORKER_CRASH` — никогда не повод дать воркеру ещё
раз: повтор воспроизводит то же самое. `INFRA_FAILURE` отдельно, чтобы
сетевые проблемы не съедали цикл rework.

**Каждая новая мутация проходит механику заново.** После rework
обязательно полный цикл: worker → mechanical → reviewer. Иначе
`worker → verify → reviewer → FAIL → worker → reviewer` — второй
мутации без барьера.

### 2-bis.5-bis Лимиты NIM: измерено (2026-09-30)

**Никаких rate-limit заголовков нет.** Ни `x-ratelimit-*`, ни каких-либо
других `x-*` в ответе — проверено на обычном запросе. Квоту нельзя
прочитать, её можно только упереть.

**Измерено:**

| Тест | Результат |
|---|---|
| тривиальный запрос | 200 за 1.36 с |
| `max_tokens=8000`, 7990 токенов | 200 за **89.10 с** = **89.7 ток/с** |
| всплеск 25 параллельных | **18/25 успех**, 7 × 503 «Service temporarily overloaded» |
| второй всплеск 25 сразу | **7/25 успех**, 429 «Too Many Requests» |

Главное открытие: **NIM отдаёт 503 «Service temporarily overloaded» там,
где Groq отдаёт 429.** То есть лимит NIM — это прежде всего **потолок
конкурентности**, а не запросов в минуту. Наш агент работает
последовательно с фанатной делегацией (до 10 детей, но они
разделены по времени), так что это поправимо.

Скорость 89.7 ток/с — это 5380 ток/мин на одном потоке. Если бы лимит был
8000 TPM (как у Groq), 8000 токенов заняли бы 89 с — а заняли ровно 89.10 с.
**Значит потолок порядка 8000 TPM на ключ, совпадает с оценкой Groq**, но
подтвердить без заголовков нельзя.

**Из сети (creeta.com, 2026):** массовая цифра **~40 RPM на `nvapi-`ключ,
общий пул на все модели, не на модель**. NVIDIA не публикует стабильной
таблицы лимитов для free; единственное официальное заявление (форум,
16.04.2026): лимиты «зависят от модели, сценария и текущей общей
нагрузки», и команда «не может увеличить лимиты с форума». Считай ~40 RPM
народной меркой, не SLA.

Сходится с моим замером: 25 параллельных за 1.4 с = ~1070 RPM по
проводимости, но аккуратно 18 из 25 прошло — значит потолок между 18 и 25
одновременных.

**Официальное подтверждение в форуме NVIDIA:** «The NVIDIA API catalog
offers a no-cost trial experience of NVIDIA NIM, and you may experience
extended wait times during periods of high load.»

#### Р7. Слой 6 невозможно собрать из слоёв 4-5 — разрыв стыка

Найдено сквозным прогоном. `verdict decide` делает
`json.load(open(args.mechanical))` и `json.load(open(args.review))` —

|---|---|---|
| `mechanical.py` | **нет** | **0 вхождений** |
| `reviewer.py` | **нет** | 1 (внутреннее) |
| `baseline.py` | есть | есть |

**Ни механика, ни рецензент не умеют отдать результат машиночитаемо.** Оба
печатают только текст. Значит слой 6 в текущем виде не подключается к
реальному выходу слоёв 4-5 через командную строку.

**Почему не поймали 190 зелёных тестов:** `test_verdict.py` (19 групп)
проверяет слой 6 на рукописных JSON-фикстурах. Фикстуры написаны в том
формате, которого реальные слои не производят. Это ровно тот класс
доказанного дефекта, о котором предупреждал этот же документ: слои,
проверенные по отдельности.

**Починка:** добавить `--json` в оба CLI. Данные уже есть — `mech.run()`
возвращает dict, рецензент возвращает dict. Нужен `json.dumps(result)` в
stdout. Плюс тест «CLI отдаёт валидный JSON».

**ЗАПРОС:** починить и прогнать связку заново, убедившись что `decide`
принимает реальные результаты слоёв, а не фикстуры.

#### Р8. `check.split()` ломается на пути с пробелом

`execute_criteria` исполняет `check.split()` — простое разбиение по
пробелам. Кавычки в пути остаются частью токена, и команда падает с
`exit=2`, что неотличимо от «проверка провалилась». На `A:\` и `Z:\` работает,
на любом пути с пробелом сломается.

Симптом совпадает с ошибкой самой проверяемой логики, поэтому легко
выдаётся за баг механики. На этом споткнулся мой собственный стенд первым.

**ЗАПРОС:** `shlex.split(check, posix=False)` либо список аргументов в
спецификации.
