## Что сделано

`auxiliary.review` настроен на **NIM** (`provider: nvidia`,

## Почему отклонился

### 1. Groq отвечает 403 с этой машины

Живая проверка трёх рельсов, одна VPN-сессия, 2026-09-30:

| Рельс | HTTP | Время |
|---|---|---|
| OpenRouter `nemotron-3-ultra:free` | **200** | 1.51 с |
| NIM `openai/gpt-oss-20b` | **200** | 1.51 с |
| Groq `openai/gpt-oss-120b` | **403 Forbidden** | — |

VPN поднят: иначе OpenRouter дал бы 403, а NIM — 451. Значит по правилу
«сначала VPN, потом ключи» VPN не при чём, блокировка на стороне Groq для
нашего egress. Это совпадает с записью в `secrets/gateway.env`: тот же
эффект указан для ASN Interhive (403) с указанием, что с другого выхода — 200.

### 2. Ключ Groq некуда положить безопасно

Провайдера `groq` в Hermes нет (это отмечено и в TODO, и в заметках по
секретам): в `plugins/model-providers/` такого каталога нет, а упоминания
`groq` в `config_defaults.py` относятся к STT.

Значит рецензент на Groq возможен только через `provider: custom`, и тогда
`api_key` пришлось бы записать в `auxiliary.review.api_key` внутри
`hermes-home/config.yaml` — а **этот файл под git**. Секрет в
git-отслеживаемом файле — недопустимо.

Дополнительно: резолв ключа для api-key провайдеров идёт через
`resolve_api_key_provider_credentials(provider_id)` c переменной вида
`<PROVIDER_ID>_API_KEY`. Для `custom` это `CUSTOM_API_KEY`; в коде
`GROQ_API_KEY` для aux-путей не используется вовсе — только для STT и
проверок подписки. То есть автоматического подхвата `GROQ_API_KEY` для
review нет, и потребовалась бы ручная правка кода апстрима — а правка
исходников Hermes запрещена решением владельца.

## Почему отклонение безопасно

SCHEME требует, чтобы рецензент был **независим** от ядра, иначе вердикт
деградирует в `SEVERE`:

- ядро — OpenRouter `nemotron-3-ultra:free`
- рецензент — NIM `openai/gpt-oss-20b`

Разные провайдеры **и** разные модели ⇒ `FULL`, требование инварианта
выполнено. Перенос рецензента на Groq не менял бы класс независимости.

## Проверка, что маршрут работает именно через Hermes

SCHEME фиксирует: «Пять интеграций не проверены через Hermes (мерили сырой
HTTP)». Проверено внутри Hermes:

- ядро: `hermes -z "Say OK only"` → 200, `session_model_usage`:
  `('nvidia/nemotron-3-ultra-550b-a55b:free', 'openrouter', 1)`
- делегация: `delegate_task` → `{"status": "completed", "summary": "PONG",
  "api_calls": 1, "duration_seconds": 2.09, "model": "openai/gpt-oss-20b"}`
  — ребёнок действительно ушёл на NIM, а не на OpenRouter

Отдельно проверено, что «PONG» не выдуман ядром: в транскрипте есть реальный
вызов `delegate_task` с `api_calls: 1`. Отсутствие дочерней строки в
`session_model_usage` — особенность логирования (таблица пишет вызовы
родительской сессии), а не признак несостоявшейся делегации.

замер, его надо брать из usage-файла или из тела ответа API, а не из
обёртки `hermes -z`.
