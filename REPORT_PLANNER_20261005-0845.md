# Отчёт планировщика: почему цепочка стояла и что её разомкнуло

Дата: 2026-10-05, HEAD на момент написания `dd3939b`.
Коммиты этой сессии: `205630e`, `aa8ca99`, `6afa9b8`, `dd3939b`.

Инвариант листа соблюдён: `TODO.md` — только нерешённое, `PASSED.md` —
закрытое. **Ничего не переносилось**: закрывать было нечего, потому что
проверка не проходила. Всё, что ниже, — это починка самой проверки.

## 1. Красный CI: одна строка, а не семь дефектов

Прогон показывал две аннотации — «exit code 1» и «exit code 2». Похоже на
две поломки. На деле это одна.

GitHub запускает тело шага `run:` как `bash -e {0}`: **errexit уже включён**,
и строка `set -uo pipefail` его не выключает — она лишь добавляет `pipefail`
и `nounset`. Дальше в шаге есть строка

```sh
out=$(python "$f" 2>&1); rc=$?
```

Она существует затем, чтобы шаг **сам** решил, что делать с кодом набора. Но
под errexit первая же команда с ненулевым кодом убивает шаг целиком — вместе
с ней умирает и цикл, который должен был собрать факты по всем наборам.

Жертва — `functions/startup/test_startup.py`. Он возвращает `2`, то есть
объявленный пропуск «нулевой прогон это не успех», и делает это на любой
не-Windows машине. Шаг умирал на нём: **exit code 2**, а в `observed.tsv`
лежало **13 фактов из 20**. Следующий шаг, сверка, честно сообщил, что семь
наборов «did not run at all», и упал с **exit code 1**.

Воспроизведено точно, без догадок:

| запуск тела шага | exit | фактов |
|---|---|---|
| `bash` (моё прежнее воспроизведение) | 0 | 20 из 20 |
| `bash -e` (как у GitHub) | 2 | **13 из 20** |
| `bash -e` + `set +e` | 0 | 20 из 20 |

Почему это стоило столько: я полчаса искал семь несуществующих дефектов,
потому что второе сообщение — «покрытие потеряно» — уводило от настоящей
причины. Логи прогона недоступны без входа в аккаунт, а диагностика жила
только там.

Что изменено в `.github/workflows/verify.yml` (коммит `6afa9b8`):

- `shell: bash` объявлен явно — поведение шага не зависит от умолчания раннера;
- `set +e` в обоих шагах, с причиной прямо рядом;
- падающий набор печатает `::error title=...::`. **Аннотация GitHub видна на
  странице прогона без входа, лог шага — нет.** Это и есть тот канал, через
  который причину удалось увидеть;
- сверка различает «фактов о прогоне нет» (окружение, код 3) и «покрытие
  потеряно» (настоящая потеря) и проверяет свежесть `observed.tsv`
  (коммит `205630e`).

Бейдж: `passing`, прогон `6afa9b8` — оба шага `success`.

## 2. Дефект, который маскировал всё остальное

`functions/search/test_search.py` искал утечку старого секрета SearXNG по
его **литералу** — и находил его самого себя, в собственном исходнике.
Проверка «его больше нет» содержала то, что искала. Такой детектор красный
всегда и не отличает «утечка осталась» от «детектор мешает сам себе».

Секрет теперь хранится только как SHA-256, кандидаты опознаются по хэшу.
Проверено на пяти случаях: чистый файл — молчит; ключ из истории в YAML, в
середине лог-строки, в верхнем регистре и внутри длинной hex-строки —
находится. Набор `11/11` (коммит `aa8ca99`).

## 3. Гейт: один закон — два вердикта

`verify.sh` содержал `SKIP_ALLOWLIST=()` — пустой массив «нарочно». Из-за
этого гейт считал **каждый** пропуск падением, тогда как CI тот же прогон
разрешает по закону `zero_checks_law.py` (`2 = объявленный пропуск`).
Семь объявленных пропусков держали гейт красным бесконечно — это и было
причиной застоя.

Правка: список наборов и минимум проверок берутся из
`functions/meta/coverage-manifest.json`, то есть из данных, а не из второй
копии правила в shell. Пропуск терпим тогда и только тогда, когда набор
выполнил не меньше `min_executed`. Код `2` при полном нуле — не падение,
код `3` — падение.

Проверено на копии: `SKIPS_TOLERATED 7 из 7`, `RESULT PASS`, `rc=0`.
Проверено и обратно: если поднять `min_executed` выше фактического, гейт
обязан сказать `SHORT RUN`, и он говорит.

## 4. Лист: шаблон был пунктом, а пункт был ненаходим

Оркестратор сутки писал:

```
verified: 'А7. Матрица «что чем проверяется»: сервер против Windows'
         is not in TOTEST.md
```

А7 лежал в `TOTEST.md` целиком. Два независимых дефекта, оба воспроизведены.

**Пункт был ненаходим.** `orch-loop.sh` берёт заголовок из `mddoc list` и
режет его `cut -c1-80`. В этом окружении `cut -c` считает **байты**, а
кириллица — два байта на букву: заголовок в 56 символов это 95 байт, его режет
на 80-м, и префикс приходит с недостроенным символом. `mddoc has` не находит
ничего. Переименование в 76 байт вернуло находку: `MD has` возвращает 0,
ровно как в продакшене.

**Шаблон выдавал себя за пункты.** `mddoc` делит файл на блоки по
markdown-заголовкам, и всё до первого заголовка уходит в preamble. Заголовок
внутри шаблона — фантомный пункт: он попадает в `list` и `count`, и
оркестратор по нему честно ждёт проверки того, чего нет. Так весь шаблон
`TOTEST.md` оказался в хвосте `TODO.md`, а `TOTEST.md` остался без своего
шаблона. Хвост убран, шаблон восстановлен как preamble, его секции теперь
жирный текст, а не заголовки. `mddoc count TOTEST.md` — 1, и это А7.

В `PASSED.md` был заголовок `## НЕ ЗАКРЫТО …` внутри закрытой записи:
второй блок, который в архиве читается как открытая работа. Понижен до
подзаголовка.

Две новые группы в матрице держат это, обе доказаны отказом при
возврате дефекта:

- `unverified items survive the machine byte budget` — только для `TOTEST.md`,
  где префикс выбирает машина и сократить его при поиске нельзя. `TODO.md` не
  подвержен: там префикс называет планировщик, а `mddoc` ищет по началу строки;
- `a sheet template is not a list of items` — секции шаблона не заголовки, а
  заголовок первого уровня, названный по имени **другого** листа, означает
  вклеенный документ. Проверка смотрит на имя, а не на уровень, потому что
  `# ПЛАН РАБОТ` и `# АРХИТЕКТУРА` — собственные разделы `TODO.md`.

## 5. Отказы выдачи: 146 штук, и все из-за одной строки

Отказ выдаётся как `ITEM: НЕТ`. Оркестратор сравнивал его так:

```sh
case "$(printf '%s' "$ITEM" | tr '[:upper:]' '[:lower:]')" in
  ''|нет|none|no)
```

`tr '[:upper:]' '[:lower:]'` **не складывает кириллицу** — проверено и при
`LANG=ru_RU.UTF-8`, и при `LC_ALL=ru_RU.utf8`, и при пустом окружении. `НЕТ`
не совпадало с образцом `нет` и уходило в `dispatch`, где отвергалось как
«нет такого пункта в TODO». Все 146 отказов — из-за этой строки.

Правка: сравнение через `grep -qiE`, которое про кириллицу знает и не зависит
от локали. Проверено на формах `НЕТ`, `нет`, `Нет`, `НЕТ.`, `Нет!`, `нет…`,
пустая, пробелы, латинские `no/NO/None` — и на настоящем пункте, который по
прежнему выдаётся.

## 8. Чего я не делал

- Не переносил ничего в `PASSED.md`: перенос означал бы «проверено», а
  проверка не проходит. Молчаливое закрытие — ровно тот дефект, который чинил.
- Не убирал пропуски из наборов, чтобы гейт стал зелёным. Пропуск Windows-only
  набора на Linux честный, и закон его объявляет. Если бы я обнулил пропуски,
  бейдж позеленел бы ложно.
- Не переписывал историю git ради старого секрета: это решение владельца, и
  группа говорит о нём вслух, а не молча.
