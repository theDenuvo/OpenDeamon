## А2-bis. Адаптер OpenCode как 24/7-эндпоинт
<!--state:implemented-->

**Постановка владельца.** Сервер используется как круглосуточный эндпоинт
кодинговых задач OpenDeamon. Значит адаптер из **А2** — не тестовая обвязка, а
рабочая поверхность сервиса, и он обязан выдерживать постоянную нагрузку.

Факты, важные именно для 24/7 (замерено 2026-10-04):

```
$ /api/info → {"version":"2.0.22", …}          # v1 не существует: 404
$ /api/session → сессий: 50                     # и растут
$ du -sh /tmp/opencode                → 332M
$ du -sh ~/.local/share/opencode      → 43M
$ systemctl → Failed to connect to user scope bus (нет DBUS/XDG_RUNTIME_DIR)
$ tmux ls → error connecting to /tmp/tmux-1000/default
```

То есть: сервис поднимается не через systemd и не через tmux (оба недоступны
без `sudo`/linger), только свой супервизор в духе
`opendeamon-automation/supervisor.sh`; сессии opencode **не убираются сами** и
уже съели 332 МБ во временном каталоге — для постоянного сервиса это утечка.

**Что сделать в А2 сверх тестового варианта.** (1) один интерфейс
`CodingSession`, два транспорта: CLI (Windows) и HTTP v2 (сервер) — как в А2;
(2) слой поверх адаптера: очередь задач, одна задача — одна сессия opencode,
идемпотентность по `task_digest`, чтобы повтор не создавал вторую сессию;
(3) авторизация на входе обязательна, адрес и пароль только из
`oc-client.env`/окружения, никаких литералов в коде; (4) health-check и
рестарт: супервизор, который поднимает эндпоинт после падения и не даёт
подняться второму экземпляру; (5) уборка: сессии opencode удаляются после
приёмки результата, `/tmp/opencode` не растёт бесконечно, срабатывание порога
диска обязано быть громким, а не «съело место и упало».

**Приёмка.** (1) задача, отданная по HTTP, доходит до opencode v2 и возвращает
непустой diff; (2) повтор той же задачи не плодит сессии; (3) убийство
эндпоинта приводит к автоподъёму; (4) после приёмки `/tmp/opencode` не растёт
на размер задачи; (5) `$0`-рельс соблюдён — только `opencode/*-free`.
